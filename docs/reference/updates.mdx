---
title: Updates
description: The session/update notification variants the adapter emits and what each maps from.
---

During a session the adapter emits ACP `session/update` notifications. This
table lists every variant and its native source.

Updates remain deliverable between prompts. Native events and their terminal
marker share one bounded ordered channel, so pressure blocks the producer rather
than dropping or overtaking an item. If any typed update or lifecycle carrier
cannot be delivered, the adapter fences and contains the exact native generation.
Raw notifications are observational: failure consumes no candidate raw sequence
and typed routing continues.

## Update variants

| Variant | Emitted from |
|---|---|
| `user_message_chunk` | Replayed user messages during `session/load`. |
| `agent_message_chunk` | Newly appended native text-part content. |
| `agent_thought_chunk` | Newly appended native reasoning-part content. |
| `tool_call` / `tool_call_update` | First native tool state / later states for the same call. |
| `plan` | Native todos. |
| `usage_update` | Native token totals. |
| `available_commands_update` | Changes to the session's native slash-command set. |
| config option update | Model/mode option changes (including on `session/set_config_option`). |
| `session_info_update` | The negotiated lifecycle stream, identity-only and carrying its envelope in `_meta`. See [Prompt streaming](/docs/core/prompt-streaming). |

`usage_update` notifications may carry `_meta.opencode.messageId`; identical
snapshots for the same message are suppressed. Tool failures carry only a fixed
failure classification as structured `rawOutput`, never native handler text. A tool first observed in a terminal state uses
one terminal-status `tool_call` and does not fabricate a following
`tool_call_update`. See
[Prompt streaming](/docs/core/prompt-streaming) for how the message parts map
during a live turn.
