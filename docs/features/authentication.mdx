---
title: Authentication
description: Why the adapter advertises no ACP auth methods and how it secures the shared OpenCode runtime.
---

Provider authentication belongs to OpenCode, not to the adapter. You sign in to
your providers through OpenCode's own tooling; the adapter never manages that
credential state and never signs in on your behalf.

## No ACP auth methods

The adapter advertises an empty `authMethods` list in its `initialize`
response. An `authenticate` request is rejected with an invalid-params error
echoing the requested `methodId`, and `logout` is a no-op that clears only
adapter-owned session state — it never touches OpenCode's provider credentials.

Because provider auth is native, the [models and config](/docs/features/models-config)
option catalog is populated only from providers OpenCode is already
authenticated for.

## Runtime server credentials

The adapter's own trust boundary is the loopback link to its Agent-owned
`opencode serve` process. The server binds to `127.0.0.1` and receives a random
`OPENCODE_SERVER_PASSWORD`; all REST and SSE calls use HTTP basic auth with
that password.

<Note>
Session snapshots contain only allowlisted native sync events. Native files,
provider credentials, MCP credentials, and control secrets are never copied
into the session store.
</Note>
